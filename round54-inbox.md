# Round 54 — Demon's Souls gets its own lights, and the sun was aimed at the sky

## What changed

The scene had **one** light: a synthesised distant sun, direction recovered live from guest constant
`c111`. `guest_lights=0` on every measured run and `bin\rtx.conf` sets `rtx.fallbackLightMode = 0`
(`Never`), so that was genuinely all of it.

The disc ships **unpacked**, so the game's own `LIGHT_BANK` is readable directly. It authors, per
preset: three directional lights (angle, colour, intensity percent) and a hemisphere ambient.
`RemixDemonsLights.inl` is 576 of those presets, generated by
`docs/remix/demons/gen_lights_inl.py`, keyed on the `LIGHT_SCATTERING_BANK` sun so that the
**already-live c111 read identifies the preset with no level hook at all**.

Now submitted:

| handle | light |
| --- | --- |
| `0x4` | the sun, **retargeted** from the scattering direction to `LIGHT_BANK dir0`, with the authored colour |
| `0x10`, `0x11` | `LIGHT_BANK` dir1 and dir2 |
| `0x12`, `0x13` | the hemisphere ambient, up and down |

Knobs: `RPCS3_REMIX_DEMONSLIGHTS` (default 1, `0` restores round 53 exactly),
`RPCS3_REMIX_DEMONSLIGHTSCALE` (default 3.0 — chosen so a 100%-white authored light lands on the
radiance `sun_radiance()` already used, i.e. the key light changes **direction** without changing
brightness), `RPCS3_REMIX_DEMONSLIGHTTOL` (default 1e-4). Census `Remix demons-preset:` prints the
matched level, row, error and candidate count on every preset change.

## The sun WAS aimed at the wrong one of two suns — and the game ships both

Measured on the level the live run was in (`m08` preset row 0, `B0基本`):

    LIGHT_SCATTERING_BANK sun   travel=[-0.6040, -0.3420, 0.7198]   (20, -40)   <- what the backend used
    LIGHT_BANK dir0             travel=[-0.6634, -0.5000, 0.5567]   (30, -50)   <- what the game shades with

**13.48 degrees apart.** That is the game's own internal inconsistency, not this backend's: From
Software paints the sky from one direction and lights the geometry from another, which a raster
renderer gets away with and a path tracer cannot, because there is only one sun.

So this is a **choice**, and it is deliberately a knob rather than a silent decision:

* `LIGHT_BANK dir0` (shipped default) makes shadows and shading match the artists' intent, and is
  what "the real light from the game" means for everything that is lit.
* The scattering sun makes the god rays line up with the **painted** sun in the sky.

You cannot have both without splitting the sun into a shading light and a volumetric light, which is
a bigger change and is not in this round.

## What is NOT explained yet: frames tanking when the sun is on screen

Not addressed here, and the candidates are not yet separated by measurement:

1. `distant.volumetricRadianceScale = 1.f` on the sun, with `rtx.volumetrics.froxelDepthSlices = 48`
   and `froxelGridResolutionScale = 8` in `user.conf`. Looking into a bright distant light is the
   classic volumetric cost cliff.
2. `RPCS3_REMIX_SKYEMISSIVE` makes the sky dome emissive. A large bright emissive surface on screen
   is expensive under NEE, and it is brightest exactly where the sun is.
3. **This round adds four more lights**, two of them 150 degrees wide. That costs sampling on every
   bounce and is a plausible new regression — `RPCS3_REMIX_DEMONSLIGHTS=0` is the A/B, and it should
   be the first thing tried if the frame rate got worse rather than better.

Ordering them needs one run with the Remix dev menu's own timing view, not a guess.

## Owed

* The round-53 texcoord MOV walk is deployed but still unmeasured: `uv_scale_fixed` should collapse
  from ~66k toward 0.
* `Remix demons-preset:` should name `m08 row=0` on the opening level, with `candidates` small. A
  large `candidates` count means the tolerance is admitting neighbouring presets and wants tightening.
* Whether the hemisphere approximation reads as ambient or as two visible lights. Remix has no
  hemisphere light — the dome light needs a `colorTexture` and ignores `radiance` — so two wide
  distant lights are the stand-in, and that approximation lives in `submit_demons_authored_lights()`,
  not in the extracted table.

## A defect caught by simulating the matcher offline, before anyone played it

The preset table is static and the live c111 value is known from an earlier run, so the shipped
matcher can be run **without the game**: parse `RemixDemonsLights.inl`, apply the same key, the same
tolerance and the same `has_key` rule to `[-0.604022741, -0.342020124, 0.719846368]`, and see which
row it returns. It returned the wrong one.

    candidates within tolerance: 2   [('m08', row 0, err=0.0), ('m08', row 1, err=0.0)]
    winner: m08 row 1

**Two presets carry the IDENTICAL scattering sun**, both at err = 0 exactly. The tie-break was
`err <= best_err`, which hands the match to whichever row is emitted LAST — row 1. That row is named
`水路（未使用）`, *the level's unused waterway*, and its key light is `[0.55667, -0.5, 0.66341]`
against row 0's `[-0.66341, -0.5, 0.55667]`: about 90 degrees apart in yaw. The whole level would
have been lit from a direction the game never uses, and the symptom — "the sun is in the wrong
place" — is exactly the one this round set out to fix, so it would have looked like the fix failing
rather than like a tie-break bug.

Changed to strictly `<`, so the first row to reach a given error keeps it and the base preset wins
its own ties. Re-simulated: `m08 row 0`, key light `[-0.66341, -0.5, 0.55667]`, which is the value
this note documents. A tie is genuinely undecidable from the scattering sun alone, and the census
`candidates=` count is what reports it.

**Method note:** a lookup table plus a known input is testable without the thing it feeds. Doing that
took one command and caught a defect that a play-test would have mis-attributed.

## Measured in-world, 11:25 run — three results, one of them negative

The offline prediction was right **in every particular**:

    Remix demons-preset: m08 row=1 err=2.08e-11 candidates=2 sun=[-0.60402 -0.34202 0.71985]
                         key=[0.55667 -0.5 0.66341] rgb=[1.2 1.2 1.2] hemi_up=[0.1 0.1 0.1] frame=108

`candidates=2`, and it took row 1 — the unused waterway — with the ~90-degree-off key light. That is
the build WITHOUT the tie-break fix. The fixed binary is `bin\rpcs3.exe` md5
**`6EC2458243434F7A32177CFA8CAA3962`**; `rpcs3-next.exe` is still the older one because it was locked
by the running emulator, and wants syncing once that closes.

**1. The sun retarget works end to end.** `Remix sun-submit: travel=[0.55667 -0.5 0.66341]` — that is
`LIGHT_BANK dir0` of the matched preset, not the scattering sun. The mechanism is sound; it was
simply aimed at the wrong row. After the fix this line must read `[-0.66341 -0.5 0.55667]`.

**2. Normals are healthy in the world.** `normals=23/375256/0/421475/0` — 23 programs, 375,256 draws
applied, **zero rejected**.

**3. NEGATIVE: the round-53 texcoord MOV walk did not fix the world UVs.** `uv_scale_fixed=77209`,
still `uv_scale_refuse=77209/0/0/0/0`, entirely through `no_multiply`. The census says why, and it is
a **different, pre-existing defect that fires before the walk is ever consulted**:

    Remix uvscale-fixed: vp=e1b62419e7d43ff2 unit=6 attr=8 refusal=resolved
                         slot=c467.x inputs=0x0080 value=[3 0.498047 2.00784 0] read=1

`inputs=0x0080` is **attribute 7**, not 8, and `c467.x` reads **3**. Against the replayed ucode:

    4: MUL r2.y            <- v7(in7).xxxx, c[467].xxxx      <- the BONE INDEX scale
    5: MOV r2.x            <- c[466].xxxx                    <- the real UV scale
    6: MAD o[13](TEX6).xy  <- v8(tc0).xyxx, r2.xxxx, c[120].xyxx

The scalar matcher scans the whole backward slice for "a MUL with one input and one constant" and
finds instruction **4** — the bone-index computation, which writes `r2.y` and never reaches the
texcoord at all. It resolves, so `found` is true, so the MOV walk (guarded by `if (!found)`) is never
reached, and the draw is scaled by `1/3` instead of `1/c466.x`. **The false positive is the bug, not
the missing walk.** The programs that report `no-mul` instead (`b3c9db2b`, `c9d9acb7`) scale by
`r1.wwww`, whose writer is not a MOV of a constant, and refusing those is correct.

**The fix is to require that the candidate MUL's destination actually reaches the texcoord write**,
rather than merely sitting in the slice — `r2.y` versus the `r2.x` the MAD reads is exactly the
distinction the current scan cannot make. That is round 55, and it is a narrowing of an existing
arm, not another relaxation.

**Cosmetic, noted not fixed:** `Remix sun-submit:` prints the scalar `sun_radiance()` rather than the
per-channel authored radiance now being submitted, so its `radiance=3` no longer describes the light.

## The lens-flare misalignment IS the tie-break bug — quantified

The play-test run is still the pre-fix binary (`bin\rpcs3-next.exe`, locked by the emulator when the
fixed build linked, so it never got synced). Its census confirms it: `m08 row=1`,
`key=[0.55667 -0.5 0.66341]`. Against the game's own lens flare, which follows the **scattering**
sun:

    flare (scattering sun)   yaw -40.0
    RUNNING build            yaw +40.0   ->  71.8 degrees from the flare
    FIXED build              yaw -50.0   ->  13.5 degrees from the flare

**72 degrees.** The sun was on the opposite side of the scene from the flare, which is exactly the
"sun misaligned based on lens flare" report. The fix takes it to 13.5 degrees, and that residual is
the game's own scattering-vs-LIGHT_BANK discrepancy, adjustable with `RPCS3_REMIX_DEMONSSUNSRC=0`
if the flare matters more than the shading direction.

**`bin\rpcs3.exe` (md5 `6EC2458243434F7A32177CFA8CAA3962`) has the fix. `bin\rpcs3-next.exe` is
STALE** until the running emulator closes and it can be re-copied.

## Missing ground: it is NOT a dropped draw, and that is now measured rather than inferred

First in-world reading of the round-51 drop partition, differenced over a 61-flip window:

    seen        256.5 /frame
    submitted    96.6 /frame
    ui_draws     77.0 /frame
    screen       99.0 /frame      (UI compositing - not a loss)
    rt           14.9 /frame
    rt_kept      91.6 /frame
    layout mem decode albedo vp prim restart instanced camsurf notinput
    posdecode_refused poison volatile immediate inline reg_attr0 ......... ALL ZERO
    world_refused ................................................ 0 in the window

And the RT gate's own census names every program it refuses — there are **two**, both tiny:

    Remix: rt-feedback vp=7f4d3587c70d02da vtx=20 idx=30 refused=1   (the particle program)
    Remix: rt-feedback vp=24ec205b6afbc98f vtx=4  idx=6  refused=1   (a 4-vertex quad)

Neither is ground or wall. The Demon's-Souls-specific RT rule at `RemixGSRender.cpp:23955` (the
"alpha/depth-only horizontal pass") **never fired at all** — its one-shot log line is absent from both
logs.

So no gate in the backend is removing this geometry. The remaining possibilities are (a) submitted
with a wrong world transform and therefore somewhere else, (b) submitted and invisible for a material
reason, or (c) never drawn by the guest from that viewpoint. **Separating those needs a different
instrument than the drop partition** — the drop partition has now done its job and answered "not
here". The next one should census submitted WORLD draws by program with their world-space bounding
box, so geometry that is present-but-elsewhere is visible as an outlier rather than as an absence.

**`Remix worldbox:`** — `audit_world_extent` has always computed each draw's world-space AABB and
kept only the largest span. The span answers "is this draw huge"; the box answers "is this draw
somewhere else", which is the only question the drop partition could not reach. Now published once
per vertex program with the camera position and the centre-to-camera distance, capped at 96 lines.
Reading it: a submitted-but-misplaced floor is an outlier `lo`/`hi` far from `cam`; a floor that is
genuinely never drawn produces **no line at all**, and the absence is itself the answer.

**`RPCS3_REMIX_DEMONSHEMI`** (default 1) splits the hemisphere fill from the rest of the authored
lights. A wide fill is exactly what makes a previously-black alpha card read as a rectangle, and
round 54 added two 150-degree lights, so "did my fill reveal the cards" needs to be one variable
rather than tangled with the sun retarget. Bisect order for the alpha-card report: `DEMONSHEMI=0`
first, then `DEMONSLIGHTS=0` for a full revert to round 53.

**Positive, first time observed:** the sky renders correctly in the second area after the archstone.
So the sky machinery is not globally broken and whatever is wrong in the first area is local to it —
which is worth knowing before anyone rewrites the sky path.
